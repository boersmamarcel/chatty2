# Swarm vs single agent: paired benchmark (2026-10-02)

**When to read this:** you want to know whether a Chatty team (the frozen
presets `data-analysis`, `fix-and-verify`, `research-brief`) beats one
harness agent with the same tools on the EV-3 task set, and at what cost.

Generated by `scripts/swarm-bench/report.py` from the results of
`scripts/swarm-bench/run.sh`; the protocol is fixed in
[`swarm-vs-single-prereg.md`](./swarm-vs-single-prereg.md).

## Read this first

- **Both arms solved all 30 tasks.** The primary metric hit the ceiling, so
  it cannot tell the arms apart. With 30/30 on both sides, the paired
  difference is exactly 0, and the Wilson lower bound of 88.6 % is the most
  the data says about either arm. The pre-registered MDE (26–40 pp) did not
  come into play: there was no variance to detect anything with. The task set
  turned out easier for this model than planned.
- **Cost and time separate the arms cleanly.** The team used **3.3× the
  tokens** (95 % CI 2.8–3.9) and took **6.9× the wall time** (95 % CI
  5.9–8.1) for the same result. The family breakdown runs the same way: the
  data-audit team cost the most (4.8× tokens, about 9× wall), code fix the
  least (2.4× tokens).
- **The run was clean.** It had no timeouts, no crashes, no server errors
  and no invalid handoffs. The shared-server throttle held requests for 27 s
  in total over the 2 h 15 min run. Every deliverable was found in the
  leader's own workspace or final answer: each team merged or relayed its
  workers' output.
- **What this does not show.** These are short, well-specified tasks, one
  trial each, on one 27B model with thinking off. Harder or longer tasks
  could separate the arms on success. Whether a team wins there is still open.

## Against the literature prior

**The result agrees with the prior.** The prior predicted that the swarm
does not beat one agent on sequential, tool-heavy work and costs more:

- every multi-agent variant lost 39–70 % in Kim et al.
  ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296));
- below a capability threshold, a rigid structure beats autonomy
  ([arXiv 2603.28990](https://arxiv.org/abs/2603.28990)).

Here the swarm did not lose on success, which is milder than Kim et al.'s
loss, but it paid 3–7× in tokens and time for no gain. Our own E8 run
([`dabstep-team-2026-09-30.md`](./dabstep-team-2026-09-30.md)) points the
same way: `analyst-panel` scored 63/80 against 64/80 for one agent, at about
3× the tokens and 9× the p50 time.

The difference is that the shipped presets had **no** invalid handoffs here,
where invalid handoffs were E8's main failure. Short, single-hop handoffs
between a leader and one or two workers worked reliably on this model.

## Recommendation

On this model and task set, a Chatty team is not worth its cost. The
shipped team presets matched one agent with the same tools at 100 % success,
at about 3.3× the tokens and 7× the wall time. By the pre-registered rule
(`NO_DETECTABLE_DIFFERENCE` → no evidence that the swarm is worth its cost),
the recommendation is:

- **Keep teams experimental** and do not make them a default.
- **Make no claim** in docs or marketing that a team is more accurate.
- **Do not build F3-style coordination features on the back of this
  result.**

Phase 2 (setups that beat one agent) needs a harder, pre-registered task set
where one agent fails often, about 40–70 % success: long multi-file fixes,
audits whose answer needs a second check, briefs with contradictory sources.
Otherwise no team can show a gain on success. When choosing what to build,
prefer structures that buy accuracy cheaply, such as the k = 3 + judge
pattern that beat majority vote on DABstep, over open delegation.
