# Pre-registration: swarm vs single agent on long multi-part tasks (EV-7)

**When to read this:** you are about to run, or read the result of, the
long-task swarm-vs-single benchmark
([AGE-826](https://linear.app/agents-research/issue/AGE-826)) and need what
was fixed before the first swarm-arm run: the arms, the task set, n, the
metrics, the analysis, the minimum detectable effects and the decision rule.

This file is frozen. `long_prereg_exists_and_is_frozen`
(`crates/chatty-tui/tests/swarm_bench.rs`) pins its SHA-256, and
`long_task_set_is_frozen` pins the task set's. A run made after any change to
either is not pre-registered. The format follows EV-3's
[`swarm-vs-single-prereg.md`](./swarm-vs-single-prereg.md); where this file
is silent, that one applies.

Committed on <freeze date>, after the single-arm calibration
([`swarm-vs-single-long-calibration.md`](./swarm-vs-single-long-calibration.md))
and before any swarm-arm run of any task in `evals/swarm-long/`.

## Question

EV-4 ([`swarm-vs-single-2026-10-02.md`](./swarm-vs-single-2026-10-02.md))
found no difference because both arms solved every task. Teams should win,
in theory, where one agent runs out of room: long tasks with many
sub-parts, where a single agent with a 32k-token window loses track,
overflows its context or skips parts. On such tasks, does a Chatty team
solve more of the work than one harness agent with the same tools and model?

- **H0:** the mean sub-part scores are equal.
- **H1 (two-sided):** they differ.

## The prior

The prior is still against the swarm, but less firmly than in EV-3.

- **Against:** Kim et al. ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296))
  found every multi-agent variant 39–70 % worse on sequential, tool-heavy
  work; our E8 (DABstep, same model) and EV-4 found the team no better at
  about 3× the tokens and 7–9× the time, with invalid handoffs as the
  team's largest failure bucket.
- **Structural handicaps of the frozen presets on these tasks:** the
  `research-brief` researcher has 8 turns and the writer 6 turns and 400
  words, against a corpus of up to 27 documents and eight questions; the
  `fix-and-verify` coder has 20 turns for five to seven issues, and the
  leader allows one review round; the `data-analysis` analyst has no shell
  (SQL only). The single agent has 100 turns.
- **For:** each team agent starts with a fresh 32k window, so a leader that
  splits the work keeps every worker's context small, which is exactly where
  the single agent fails in calibration (it re-reads files until the loop
  guard stops it, or answers before computing).

**What the prior predicts:** Δ ≤ 0 on sub-part score, and higher tokens per
solved sub-part for the swarm. Stated belief before the run:
P(`SWARM_BETTER`) ≈ 0.15, P(`SINGLE_BETTER`) ≈ 0.25.

## Arms

As in EV-3: one `chatty-tui --headless --auto-approve` process per task and
arm, same prompt, model and execution settings (filesystem, shell and git on;
fetch, browser, code sandbox and memory off).

- **(i) `single`:** one harness agent, no tool profile, no team. Turn
  budget **100** (EV-3: 40; these tasks need more tool calls).
- **(ii) `swarm`:** the family's frozen team preset (`--team <preset>`), each
  agent with its spec's own turn budget, exactly as compiled into the build.

| Family | Swarm preset | Leader → workers |
|---|---|---|
| data audit (`ld*`) | `data-analysis` | `data-lead` → `data-analyst`, `reviewer` |
| code fix (`lc*`) | `fix-and-verify` | `fix-lead` → `fix-coder`, `code-reviewer` |
| research brief (`lr*`) | `research-brief` | `editor` → `researcher`, `writer`, `reviewer` |

The presets were not changed for this benchmark and were never run on its
tasks before this file was committed.

## Task set

`evals/swarm-long/tasks/`, generated by `evals/swarm-long/gen_*.py`. Each
task has 5–9 sub-parts, checked by `scripts/swarm-bench/verify.py`'s `parts`
check against the task's `check.json` (never shown to the agent):

- **Data (`ld*`):** 4–6 CSV files (thousands of rows), a data dictionary
  with business rules (re-sent rows, refunds, FX, time zones, effective
  dates, amendments) and eight questions. A part passes when the last
  `Qn: <answer>` line of `report.md` (else of the final answer) matches the
  expected value within the stated tolerance.
- **Code (`lc*`):** a stdlib Python package (`lc01`–`lc06`: 1.3k–2.5k lines,
  seven issues; `lc07`–`lc10`: 500–600 lines, five issues) with the issues
  in `ISSUES.md`, some covered by visible tests. A part passes when that
  issue's hidden test module passes on a copy of the workspace whose
  `tests/` is replaced by the hidden suite (editing a test cannot change the
  score). Each issue's fix is independent of the others
  (`gen_code.py --check`).
- **Research (`lr*`):** a corpus with superseded versions, distractors and
  stated precedence rules (`lr01`–`lr06`: 24–27 documents, 36k–41k words,
  more than a 32k-token window; `lr07`–`lr12`: the same facts and questions
  in an 11k–14k-word corpus), and eight questions. A part passes when
  `brief.md` matches that answer's pattern (the superseded value does not
  match); a ninth part checks that at least five corpus files are cited and
  nothing outside the corpus is.

A deliverable is found by EV-3's lookup for both arms (workspace root, then
the workers' worktrees, then any branch); code is judged in the workspace
root only, i.e. what the leader merged.

calibration scores, so the single arm's real-run scores on them will drift
toward their true level. The calibration runs are therefore **not** reused:
both arms are run afresh and only the fresh runs are analysed. The drift
affects the single arm's level, not the comparison, because the swarm faces
the same tasks.

## n and the minimum detectable effects

**n = 15 pairs.** Every task the calibration kept. In calibration a single-arm run took 27
minutes on average; a team run is assumed to take about 45 (capped at 50), so
15 pairs need about 18 GPU-stream-hours: about 9–10 hours of wall time on
two streams, inside the 14-hour budget.

| Endpoint | Test | MDE (α = 0.05 two-sided, power 0.80) |
|---|---|---|
| Sub-part score | sign-flip permutation (≈ paired t), SD of the per-task difference 0.68 (from the calibration replicates) | **53 pp** |
| Full pass | exact McNemar, q = 0 / 0.05 / 0.10 | 48 / 58 / 67 pp |

The SD is large because a single run of a kept task tends to score near 0 or
near 1; it comes from `scripts/swarm-bench/mde_long.py --n 15 --sd 0.68`.

**This benchmark detects only large effects.** An effect under these MDEs can
be neither shown nor excluded.

## Metrics

- **Primary: mean sub-part score** per arm (sub-parts passed ÷ sub-parts,
  averaged over tasks).
- **Key secondary: full-task pass** (every sub-part), per arm.
- **Secondary: cost.** Tokens (input + output, counted at the wire, every
  agent of a team included) per task and per solved sub-part.
- **Secondary: wall time** per run, including the shared-server waits.
- **Context:** runs with a call the server refused for its length
  (`context_errors`), and runs whose largest prompt reached 90 % of the
  window (`max_input_tokens` ≥ 29,491).
- **Invalid handoffs** (the usage file's `handoff_invalid_by_role`).
- **Failure tags** per run: timeout, context overflow / saturation, skipped
  sub-parts (an expected `Qn:` line absent), no deliverable, no delegation
  (swarm). Handoff errors and skipped code/research parts are tagged by hand
  from the transcripts in the write-up, after the numbers are final.

## Analysis

- **Primary.** Δ = mean over tasks of (swarm score − single score). The 95 %
  CI is a paired bootstrap (10,000 resamples, seed 670); the test is the
  exact two-sided sign-flip permutation test on the per-task differences
  (all 2ⁿ sign patterns).
- **Full pass.** The paired difference with a bootstrap CI and the exact
  McNemar test on the discordant pairs.
- **Cost and time.** The geometric mean over tasks of the swarm ÷ single
  ratio, with a paired-bootstrap 95 % CI; tokens per solved sub-part as a
  plain ratio of the two arms.
- `scripts/swarm-bench/report_long.py` computes all of it.
- **Every finished run counts.** A timeout, a crash or a missing
  deliverable scores what the verifier finds (usually 0).
- **The one exception.** If the model server itself fails (connection
  refused, HTTP 5xx, a restart) or the host reboots during a run, that run
  is re-run once and the report says so. No run is re-run because of its
  outcome.

## Decision rule

- **`SWARM_BETTER`:** Δ > 0 and permutation p < 0.05.
- **`SINGLE_BETTER`:** Δ < 0 and permutation p < 0.05.
- **`NO_DETECTABLE_DIFFERENCE`:** otherwise, read together with the MDE.
- **Worth its cost:** only `SWARM_BETTER` with tokens per solved sub-part at
  most 2× the single agent's. Anything else: no evidence that the swarm is
  worth its cost on long tasks, and teams stay experimental.
- **Full pass** is reported with its McNemar p but does not decide the
  verdict (it is underpowered at this n, see the MDE).
- **Agreement with the prior:** *agrees* when Δ ≤ 0 and the swarm's tokens
  per solved sub-part are higher; *contradicts* it on `SWARM_BETTER`;
  otherwise neither.

## Stopping rule

- **Runtime budget: 14 hours** of wall time from the first run, not counting
  time the host or the server was down. If it runs out, the run stops after
  the last complete pair and that prefix is analysed, labelled
  "pre-registered subset, k of n", with the MDE for k.
- A container, server or host restart is not a stop: the run resumes with
  the same run id (finished runs are kept).

## Not allowed

- Tuning a preset, a prompt or a task after this file is committed.
- Dropping or adding tasks after the run starts.
- Reporting a family alone as the headline result.
- Re-using calibration runs in the analysis.
