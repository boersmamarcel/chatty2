# Pre-registration: swarm vs single agent (EV-3)

**When to read this:** You are about to run, or read the result of, the
swarm-vs-single benchmark (EV-4, AGE-671) and need what was fixed before the
first real run: the arms, the task set, n, the metrics, the analysis, the
minimum detectable effect and the decision rule.

This file is frozen. `prereg_exists_and_is_frozen`
(`crates/chatty-tui/tests/swarm_bench.rs`) pins its SHA-256. A run made after
any change to it is not pre-registered. The protocol follows
[`experiment-protocol.md`](./experiment-protocol.md): paired runs, success
rate, cost and wall time, and a stated MDE.

Committed by EV-3 ([AGE-670](https://linear.app/agents-research/issue/AGE-670))
on 2026-10-02, before any real-model run of the task set.

## Question

Does a Chatty team (a leader that delegates to specialised workers) solve
more tasks than one harness agent with the same tools and the same model?
If it does, is the extra cost worth paying?

- **H0:** the success rates are equal.
- **H1 (two-sided):** they differ.

## The prior

The prior is against the swarm.

- **Kim et al. ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296)):** on
  sequential, tool-heavy work, every multi-agent variant lost 39–70 %
  relative to one agent.
- **[arXiv 2603.28990](https://arxiv.org/abs/2603.28990):** below a
  capability threshold, a rigid structure beats autonomy.
- **Our own E8** ([`dabstep-team-2026-09-30.md`](./dabstep-team-2026-09-30.md)):
  on DABstep subset-80 with the same local model, the `analyst-panel` team
  scored 63/80 and one agent scored 64/80. The team used about 3× the tokens
  and took about 9× the p50 wall time. Invalid handoffs were its largest
  failure bucket.

**What the prior predicts here:** the swarm's success rate is no higher than
the single agent's, and its tokens per solved task are higher.

## Arms

Both arms run one `chatty-tui --headless --auto-approve` process per task,
with the same prompt, model and execution settings. Fetch, browser, code
sandbox and memory are off. Filesystem, shell and git are on.

- **(i) `single`:** one harness agent with no tool profile and no team. It
  gets every tool the execution settings allow. That covers the union of the
  team's tool profiles (`coordinator` ∪ `coder` ∪ `reviewer`) except the
  delegation tools, which need a roster. Turn budget: 40.
- **(ii) `swarm`:** the family's team preset, `--team <preset>`, exactly as
  compiled into the build that runs. Each agent keeps its own turn budget
  from its spec.

| Family | Swarm preset | Leader → workers |
|---|---|---|
| data audit | `data-analysis` | `data-lead` → `data-analyst`, `reviewer` |
| code fix and review | `fix-and-verify` | `fix-lead` → `fix-coder`, `code-reviewer` |
| research then write | `research-brief` | `editor` → `researcher`, `writer`, `reviewer` |

**Deviation from the spec.** The spec (vault
`dev/projects/fabric-evals-and-gate.md` §4.1) names one frozen swarm preset,
the `analyst-swarm` of EV-1. That preset was built and then dropped on
product grounds in AGE-752 (see
[`showcase-runs-2026-09-29.md`](./showcase-runs-2026-09-29.md)), and was
never merged. This benchmark instead uses the three shipped team presets,
one per family, each matched to its family. They were tuned on their own
fixtures only (the same showcase note), never on this task set, and their
prompts are frozen: a change gets a new preset name. The swarm arm is
therefore "the team Chatty ships for this kind of task".

## Task set

Thirty tasks, ten per family, in `scripts/swarm-bench/tasks/`. Each has an
automatic verifier, `scripts/swarm-bench/verify.py`, reading the task's
`check.json`, which the agent never sees.

- **Data audit (`d01`–`d10`):** a synthetic CSV generated by
  `gen_data_tasks.py` (seed 670) with one planted finding. Pass means the
  final answer's last `VERDICT:` line is the known label. If the final answer
  has no `VERDICT:` line, the run's `report.md` or `answer.txt` is read
  instead.
- **Code fix and review (`c01`–`c10`):** a small Python project with one or
  two bugs and a failing `unittest` suite. Pass means
  `python3 -m unittest discover -s tests -t .` exits 0 in the workspace and
  every test file is byte-identical to the original.
- **Research then write (`r01`–`r10`):** a corpus of 3–4 short documents in
  `docs/`, including superseded versions and distractors. There is no web
  access. Pass means `brief.md` exists and matches every fact pattern of the
  task's checklist (case-insensitive regex). It must cite at least one corpus
  file in square brackets, and it must cite no file outside the corpus and no
  URL.

A deliverable is found by the same lookup for both arms: the workspace root,
then the workers' worktrees, then any branch. A team's writer commits on its
own branch.

Task set SHA-256 (`bench.py`'s `sha256_tree` over `scripts/swarm-bench/tasks/`):
`6b18523db63b148b7607c77d3a707d608e4414cef92f11a02732576599a70264`.
Every run records it in `meta.json`, and the report prints it.

| Field | Value |
|---|---|
| Model | `RedHatAI/Qwen3.8-27B-INT4` on the local vLLM (`http://172.17.0.1:8000/v1`), 32k context |
| Thinking | off (`--think false`, i.e. `chat_template_kwargs.enable_thinking = false`) |
| Temperature | 0.3 |
| Trials | one run per task and arm |
| Order | interleaved by family (d01, c01, r01, d02, …). Even positions run `single` first, odd positions run `swarm` first |
| Per-run cap | `--max-duration 30m`; hard kill at 40 min |

## n and the minimum detectable effect

**n = 30 pairs.** Thirty fits one weekend night on the shared GPU. The
showcase runs put a team run at 2–16 minutes and a single run at about a
third of that, so 60 runs take about 5–7 hours.

The MDE is for the exact McNemar test, two-sided α = 0.05, power 0.80, by
exact enumeration over the paired outcomes. It depends on how often the arms
disagree in the direction opposite to the effect (*q*):

| Pairs | q = 0 | q = 0.05 | q = 0.10 |
|---|---|---|---|
| 30 (this run) | 26 pp | 34 pp | 40 pp |
| 60 (for reference) | 13 pp | 21 pp | 25 pp |

**This benchmark detects only large effects.** At a single-agent rate of
about 80 %, the prior's 39 % relative loss is about 31 pp, which is near this
MDE. A difference under about 26 pp can be neither shown nor excluded.

## Metrics

- **Primary: success rate.** Solved / 30 per arm, with a Wilson 95 % CI.
- **Secondary: cost.** Tokens (input + output) per solved task. Tokens are
  counted at the wire by the harness's meter, every agent of a team included.
  The local model has no price, so tokens are the cost.
- **Secondary: wall time.** Per run, including the shared-server waits.
- **Descriptive:** results per family (ten pairs each, not powered),
  timeouts and crashes, runs with server errors, invalid handoffs (from the
  usage file's `handoff_invalid_by_role`), and the verifier's failure reasons.

## Analysis

- **Paired difference.** Δ = rate(swarm) − rate(single). The 95 % CI is a
  paired bootstrap (10,000 resamples, seed 670). The test is the exact
  McNemar test on the discordant pairs.
- **Cost and time.** The geometric mean over tasks of the swarm ÷ single
  ratio, with a paired-bootstrap 95 % CI. Tokens per solved task are also
  reported as a plain ratio of the two arms.
- **Every finished run counts.** A timeout, a crash or a missing deliverable
  is that arm's failure.
- **The one exception.** If the model server itself fails (connection
  refused, HTTP 5xx, a restart) during a run, the pair is re-run once and the
  report says so. No run is re-run because of its outcome.

## Decision rule

- **`SWARM_BETTER`:** Δ > 0 and McNemar p < 0.05.
- **`SINGLE_BETTER`:** Δ < 0 and McNemar p < 0.05.
- **`NO_DETECTABLE_DIFFERENCE`:** otherwise. This is read together with the
  MDE: an effect under the MDE is not excluded.
- **Worth its cost:** only `SWARM_BETTER` with tokens per solved task at most
  2× the single agent's. Anything else means there is no evidence that the
  swarm is worth its cost on this task set, and the teams stay experimental.
- **Agreement with the prior:**
  - it *agrees* when Δ ≤ 0 and the swarm's tokens per solved task are higher;
  - it *contradicts* the prior on `SWARM_BETTER`;
  - otherwise it is reported as neither.

## Stopping rule and subset

- **Runtime budget: 10 hours** of wall time. If the run would exceed it, it
  stops after the last complete family triple (dNN, cNN, rNN), and that
  prefix is analysed. The prefix is balanced across families by construction.
- **Labelling.** The report then says "pre-registered subset, k of 10 per
  family", and the MDE row for that n is the one that applies.

## Plumbing check

Before the run, the harness is checked twice. Neither check uses a task of
this set, and neither counts.

- **The fake model.** `swarm_bench_dry_run` runs on it in CI.
- **The real model.** One pilot per arm runs on the team presets' own
  showcase fixtures, not on this task set. It confirms that both arms reach
  the server through the meter.

If a harness bug (not a model failure) invalidates runs, the bug is fixed,
the affected runs are re-run, and the report lists the fix.

## Not allowed

- **Tuning a preset or a prompt** after seeing results. The presets are
  frozen, and the task prompts are frozen with this file.
- **Dropping or adding tasks** after the run starts.
- **Reporting a family alone** as the headline result.
