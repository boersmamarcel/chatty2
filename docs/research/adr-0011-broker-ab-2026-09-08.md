# ADR-0011 kill criteria — `sub_agent` vs the broker (AGE-302)

**When to read this:** You are deciding whether A2A stays ADR-0011's wire format, or
whether the local runner should move in-process. This is the measurement that decides it.

Measured 2026-09-08 on chatty2 `abf0295a`, `release` build, by
`scripts/broker-ab-measurement.sh` driving
`crates/chatty-tui/examples/broker_ab.rs`.
Re-run it with `RUNS=10 OLLAMA_MODEL=<model> scripts/broker-ab-measurement.sh`.

## Verdict

| Criterion | Result |
|---|---|
| **1 — progress survives the round trip** | **Does not fire.** Every progress class the parent renders today survives, in order. The broker path is a strict superset: it also streams the answer. |
| **2 — the hop costs no more than ~20 ms at P50** | **Does not fire.** Median paired delta **+3.0 ms** and **+0.4 ms** in two configurations. |

ADR-0011's `## Reversal` section is not triggered. A2A stays the wire format; the local
runner stays out of process.

## Setup

| | |
|---|---|
| Host | Intel i9-10940X, 28 threads, 125 GiB, NVIDIA RTX 3090 |
| Kernel | Linux 6.8.0-138-generic, Ubuntu 24.04 |
| Build | `release`, chatty2 `abf0295a` |
| Provider | Ollama at `http://localhost:11434`, same model on both arms |
| Runs | 10 per arm, **interleaved**, after one warm-up per arm |
| Isolation | neither arm gets a `git worktree` — the criterion is about the hop |
| VM | none, as the issue specifies |
| Config | a throwaway `XDG_CONFIG_HOME`, so no real chatty setup or API key is in scope |

Both arms delegate the *same fixed task* to the *same binary* (`chatty-tui`), resolved the
same way (`chatty_core::tools::worker_executable`), with the same approval policy and the
same worker isolation. The two paths differ in the hop and nothing else — that is a
property of the code, not of the harness: AGE-301 moved worker isolation and the
executable lookup into functions both paths call.

### Why two configurations

A hop worth ~20 ms cannot be resolved against a model turn whose own variance is tens of
milliseconds, so the run is split by what each configuration can answer:

* **A — latency.** `qwen2.5:0.5b`, a task with no tool call, ~215 ms per turn. The
  smallest model time available, so the hop is the largest possible fraction of it.
* **B — progress.** `llama3.2:3b`, a task that makes a real `read_file` call, ~2.3 s per
  turn. Big enough to actually use a tool, which is what criterion 1 is about.

Both report latency; B is the honest reminder that a 20 ms question against a 2.3 s turn
is answerable only because the runs are paired.

## Criterion 2 — the hop

The deciding statistic is the **paired** delta, not the difference of two independent
P50s. The arms alternate, so drift in machine load or model-server state lands on both
members of a pair and cancels. Over ten samples the unpaired difference is dominated by
the model turn's own variance; the paired one is not.

### A — `qwen2.5:0.5b`, no tool call

| arm | P50 ms | P95 ms | min | max | mean |
|---|---|---|---|---|---|
| `sub_agent` | 211.0 | 239.6 | 201.6 | 239.6 | 214.0 |
| broker | 217.3 | 234.6 | 210.1 | 234.6 | 219.2 |

| statistic | value |
|---|---|
| P50(broker) − P50(sub_agent) | +6.2 ms |
| **median paired delta** | **+3.0 ms** |
| P95 paired delta | +24.6 ms |
| broker slower in | 6 of 10 runs |
| paired deltas (ms) | −24.5, −8.4, −3.8, −2.7, **+3.0**, +13.3, +13.6, +13.8, +23.6, +24.6 |

### B — `llama3.2:3b`, one `read_file` call

| arm | P50 ms | P95 ms | min | max | mean |
|---|---|---|---|---|---|
| `sub_agent` | 2277.1 | 2301.5 | 2235.9 | 2301.5 | 2275.1 |
| broker | 2283.5 | 2297.7 | 2268.0 | 2297.7 | 2281.7 |

| statistic | value |
|---|---|
| P50(broker) − P50(sub_agent) | +6.4 ms |
| **median paired delta** | **+0.4 ms** |
| P95 paired delta | +47.6 ms |
| broker slower in | 6 of 10 runs |
| paired deltas (ms) | −16.8, −4.7, −3.8, −2.0, **+0.4**, +7.0, +7.5, +14.9, +15.0, +47.6 |

**Reading it.** The broker is slower in 6 of 10 pairs in both configurations — a
coin flip, not a signal — and the median cost is single-digit milliseconds. The sign
flips between pairs, which is what a difference below the noise floor looks like. The
distribution is wide relative to the effect (P95 +24.6 ms and +47.6 ms), so the honest
claim is *"the hop is not more than about 20 ms"*, not *"the hop is 3 ms"*. That is
exactly the claim the criterion asks for.

Why it is this small: the hop is a Unix-socket write and an HTTP read on loopback, both
microseconds, against a process spawn both arms pay for identically. ADR-0011 predicted
this ("per-message hop cost is microseconds and does not matter"); the measurement is
the check, not the prediction.

## Criterion 1 — the progress diff

### The live diff (configuration B, 10/10 runs identical)

`sub_agent` — 4 events per run, every run:

```
Started(sub_agent)
Text("read_file")
Text("✓ read_file")
Finished(success=true)
```

Broker — 35 events per run, every run:

```
Started(local-agent)
Text("read_file")
Text("✓ read_file")
Text("<thinking") … Text(">")      ← 31 assistant-text chunks, streamed
Finished(success=true)
```

| | `sub_agent` | broker |
|---|---|---|
| Count | 4 | 35 |
| Order | start, tool, tool result, finish | identical, plus text |
| Tool names | `read_file`, `✓ read_file` | `read_file`, `✓ read_file` |
| Interleaved text | none — the answer only arrives at the end, on stdout | streamed as artifact chunks |
| Final response | identical | identical |

**Nothing is lost; text is gained.** The `CHATTY_EVENT` path cannot carry assistant text
at all — `format_event_line` drops `Text` on purpose, because the answer is the child's
stdout. Over the broker it arrives as artifact chunks while the turn is still running. The
broker path is a strict superset, which is the direction the criterion cares about.

The tool lines are byte-identical because they are produced by the same function:
AGE-301 made `chatty_core::tools::progress_text_for_event` public rather than letting the
child re-render them, precisely so this comparison could not be gamed by two spellings
of the same event.

### The exhaustive diff

A live model calls whichever tools it feels like, so the live run is a weak instrument
for a *completeness* question. The complete answer is
`crates/chatty-tui/src/participant/equivalence.rs`,
which runs in CI: for all eleven scripted scenarios both frontends are characterized
against — tool round-trips, failing tools, stream errors, cancellation, clarification,
sub-agent progress — it diffs the parent's rendered trace between the two paths and
asserts equality after subtracting exactly the text chunks the direct path cannot carry.
That test, not this document, is what keeps the criterion answered as the code changes.

## What this does not establish

* **Hosted.** Same host only, as the issue specifies. The vsock hop (AGE-307) is a
  different measurement, on top of ADR-0010's restore-to-first-token numbers (AGE-286).
* **Concurrency.** One worker at a time. Per-endpoint budgets are AGE-305, and the
  binding limit on parallel local agents is the model server's parallel-request budget,
  not the broker.
* **Ten samples.** P95 over ten runs is the maximum; the tables say so rather than
  interpolating. The criterion is a threshold test on the median, which ten paired
  samples support; a tighter estimate of the hop itself would need a different design.
* **The worker's model.** The broker spawns workers on their configured default model,
  not the parent conversation's — A2A has no request field to carry one. Both arms were
  pinned to the same model here, so the comparison is unaffected, but the limitation is
  real and is carried as an open question on AGE-301.
